# Drawsy AI Landing

Maintainer guide for `landing_web`. This is the public website and the account/billing surface at `app.drawsyai.tech`; it is not the Canvas, sync engine, entitlement authority, or Razorpay webhook service.

## System boundary

```text
Canvas (drawsyai.tech) ───────────────┐
                                      │ direct API calls
Landing (app.drawsyai.tech) ── BFF ──┼──> Drawsy backend ──> Razorpay
       marketing, auth, billing       │       UID, sessions,
                                      │       entitlements, billing state
Firebase Auth exists at each browser origin; the backend links both through the same Firebase UID.
```

The three runtime responsibilities are deliberately separate:

- `landing_web` owns marketing/content, SEO, the login/profile/billing journeys, and the browser-side handoff UI.
- `excal-ai/excal-ai` owns the local workspace, Canvas behavior, cloud sync clients, presentations, Kanban, comments, and the Canvas-side logout/data lifecycle.
- `drawsy-ai-backend` owns Firebase-token verification, device sessions, handoffs, capabilities, billing records, Razorpay verification, webhooks, and entitlement decisions.

Landing does not proxy normal Canvas data or grant Pro locally. A browser can alter its UI or request payloads; the backend must still independently authenticate, authorize, validate the variant, and verify the provider state.

## Route map

Public and content routes include `/`, `/about`, `/help`, `/resources`, `/companion`, `/how-to`, `/blog`, `/compare/*`, `/use-cases/*`, `/authors/*`, `/changelog`, `/terms`, and `/privacy`.

Account and billing routes:

- `/login` — Google, X, and email/password sign-in, sign-up, verification, reset, and return routing.
- `/profile` — account display and sign-out-this-device.
- `/pricing` — public plan presentation and authenticated upgrade entry.
- `/billing` — subscription status and cycle-end cancellation.
- `/billing/start` — same-site upgrade entry that preserves the selected cadence.
- `/billing/handoff` — server-side exchange of a one-time billing handoff, then redirect to pricing or billing.
- `/auth/session-bridge` — hidden Canvas-to-Landing session bridge; it returns an opaque handoff only.

The route handlers under `src/app/api` are a thin same-origin BFF:

```text
/api/auth/bootstrap
/api/auth/handoff
/api/auth/handoff/exchange
/api/auth/logout
/api/billing/catalog
/api/billing/handoff
/api/billing/subscription
/api/billing/verify
```

They forward requests to the backend; they are not a second entitlement implementation.

Machine-readable and search routes are generated by `/robots.txt`, `/sitemap.xml`, `/llms.txt`, `/llms-full.txt`, `/blog/rss.xml`, and `/md/[...slug]`.

## Authentication and handoffs

The browser uses Firebase Auth for the user-facing sign-in. The backend session is established from a verified Firebase ID token:

```text
Firebase sign-in (Google, X, or email/password)
  → Firebase user
  → POST /api/auth/bootstrap (ID token in request body)
  → backend verifies token and returns Drawsy session custom token
  → Firebase session contains the backend Drawsy session claim

Email/password accounts must verify their email before the Drawsy session is bootstrapped. Verification and password reset emails are sent by Firebase Authentication.
```

`ensureDrawsySession()` avoids bootstrapping again when the Firebase token already carries the Drawsy session claim.

Canvas and Landing do not share Firebase storage or put a reusable Firebase token in a URL. When one surface needs to establish the other surface’s account context:

```text
source surface
  → authenticated backend creates short-lived, single-use handoff
  → only opaque code crosses origin / URL / postMessage
  → destination exchanges code server-side
  → destination receives a Firebase custom token
  → URL is immediately cleaned where applicable
```

The hidden session bridge uses an iframe and an origin-checked `postMessage` exchange. It is a convenience for an already-open Canvas, not an authorization channel. The backend remains authoritative if the code is expired, replayed, or associated with another session.

## Billing flow

```text
Canvas or Landing
  → create billing handoff with the current Firebase ID token
  → Landing exchanges /billing/handoff?code=... server-to-server
  → short-lived HttpOnly drawsy_billing_session cookie
  → GET /api/billing/catalog for public display
  → POST /api/billing/subscription for an allowlisted variant
  → Razorpay Checkout receives the backend-created subscription
  → POST /api/billing/verify with checkout result
  → backend verifies ownership, signature, variant, and provider state
  → webhook/reconciliation updates entitlement
  → account event tells open surfaces to refresh
```

Important boundaries:

- The public catalog is served by the backend through `/api/billing/catalog`. The UI may contain plan feature/copy structure, but provider plan IDs, entitlement state, and accepted prices are backend concerns.
- Checkout receives only the public Razorpay checkout key and a backend-created subscription ID. The Razorpay API secret and webhook secret never belong in this repository or any browser bundle.
- The browser never decides that a payment succeeded. A successful checkout callback is only sent to `/api/billing/verify`; Pro starts after backend verification and provider reconciliation.
- Cancellation is cycle-end only. `/api/billing/subscription` `DELETE` forwards to the backend, which owns the Razorpay subscription ID and idempotency/concurrency protection. Landing hides the action once cancellation is already scheduled.
- A failed handoff or missing billing session returns the user to the appropriate login/pricing path. It must not silently grant checkout access.

The current local billing setup is intended for Test Mode with the local backend. Keep variant selection and currency authority on the server; never add Razorpay plan IDs, amounts, or entitlement flags to client-controlled query parameters.

## Keeping Canvas and Landing in sync

The notification paths are intentionally lightweight:

- `BroadcastChannel("drawsy-account-events-v1")` reaches other tabs on the same origin.
- `drawsy_account_event_v1` is a short-lived browser marker shared across the Drawsy hosts where the browser permits it.
- A guarded `window.opener.postMessage` notifies the originating Canvas when a handoff page has a relevant account event.

These signals mean “re-check state”; they do not carry authority, billing data, or a Firebase token. A stale tab must revalidate against the backend before changing access. If Canvas is closed, the next Canvas launch observes the revoked/changed session and applies the normal local-vs-account workspace lifecycle.

Use the host-preserving helpers in `src/lib/site.ts`, `src/lib/auth/canvasHandoff.ts`, and `src/lib/auth/accountEvents.ts`. In local testing, keep the hostname consistent across both apps: use `localhost` on both or `127.0.0.1` on both. Production uses `app.drawsyai.tech` for Landing and `drawsyai.tech` for Canvas.

## Configuration

`.env.local` is ignored by Git. The landing app reads:

| Variable                               | Scope        | Purpose                                                                                                         |
| -------------------------------------- | ------------ | --------------------------------------------------------------------------------------------------------------- |
| `DRAWSY_BACKEND_URL`                   | server-only  | Backend base URL. Defaults to `http://127.0.0.1:3004` in development and the production backend URL otherwise.  |
| `NEXT_PUBLIC_DRAWSY_FIREBASE_CONFIG`   | browser      | Firebase web configuration required for sign-in. This is Firebase’s public web config, not an Admin credential. |
| `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION` | build/server | Optional Google Search Console verification value.                                                              |
| `NEXT_PUBLIC_BING_SITE_VERIFICATION`   | build/server | Optional Bing verification value.                                                                               |

Never place Firebase Admin credentials, Razorpay API secrets, webhook secrets, provider plan IDs intended to be private, or billing-session values in this app. Razorpay secrets belong only to the backend’s untracked local secret configuration.

## Local operation

For the landing app alone:

```bash
npm install
npm run dev
```

Open `http://localhost:3000`. For a real cross-surface check, also run the backend on `3004` and Canvas on `3001`. The backend URL can be overridden with `DRAWSY_BACKEND_URL` in `.env.local`.

Use the same hostname family for all three local surfaces. A login established on `localhost` is not the same browser-origin state as one established on `127.0.0.1`.

Validation commands:

```bash
npm run lint
npx tsc --noEmit
npm run build
npm run start
```

`next start` is only valid after a successful production build.

## Practical verification matrix

When changing auth, billing, or cross-surface routing, check the actual browser flow—not only a successful API response:

1. Signed-out Landing → `/login` → Google, X, or email/password sign-in → intended `returnTo` route.
2. Signed-in Canvas → Landing profile/pricing/billing → one-time handoff → no reusable token in the URL or storage.
3. Landing checkout start → billing handoff → HttpOnly billing session → Razorpay checkout → server verification → Canvas entitlement refresh.
4. Billing refresh, repeated cancel clicks, expired handoff, missing session, cancelled checkout, and a provider verification failure.
5. Logout from Landing with Canvas open, logout from Canvas with Landing open, logout while Canvas is closed, and multiple tabs with the same or different Canvas.
6. Backend unavailable during page load: Landing must fail closed for billing/auth while local Canvas work remains the Canvas app’s responsibility.

For every protected action, verify the negative path too: altered UID, plan, amount, currency, subscription ID, signature, or billing session must be rejected by the backend. A visually correct Landing state is not evidence of entitlement.

## Change rules

- Keep account and billing mutations behind same-origin route handlers and the backend’s verified session.
- Reuse `authBackend`, `billingBackend`, `assertSameOrigin`, `billingSessionCookie`, and the existing handoff/event helpers before adding another transport.
- Add new plans or prices to the backend catalog and provider mapping first; do not duplicate provider configuration in React components, URLs, or environment variables.
- Treat `BroadcastChannel`, cookies, and `postMessage` as notifications only. Never use them to grant access or transfer a raw token.
- Do not add background polling to compensate for cross-tab state. Use page lifecycle/event-driven refresh, with backend reconciliation on billing operations.
- Keep Canvas data paths in the Canvas/backend repositories. Landing should remain a control-plane surface, not a sync client.
- When adding a protected route, update both the same-origin BFF and the backend authorization/inventory tests.

## Failure semantics

- Invalid or expired handoff → no session; redirect to a safe local route.
- Missing/expired billing session → no billing mutation; require a fresh authenticated handoff.
- Checkout callback not verified → do not claim Pro; show a pending/support message.
- Account event received → refresh or return to login; do not infer the new plan from the event payload.
- Backend unavailable → preserve the user’s browser-visible page where possible, but fail closed for account/billing mutations.

This README describes the contract between the current repositories. If that contract changes, update this document with the route, ownership, security, and local verification impact in the same change.
